# Phase 12.4/4 — Resumable Scale, Checkpointing, Streamed Partial Readiness & Progress UI

**Goal:** scale Konusbitr's document pipeline to seamlessly process massive 900-page scans without OOM crashes, enable checkpointed resumption across worker restarts, stream partial readiness for immediate chat over early pages, and deliver a production-grade progress and recovery UI.

## Context

Phases 12.1/4 through 12.3/4 delivered the core OCR engine, multilingual capabilities, and VLM pipelines. However, enterprise documents often span hundreds of pages: 300-page regulatory filings, 500-page litigation discovery bundles, and 900-page scanned manuals.

Processing documents at this scale presents four critical challenges:
1. **Memory Blowup:** Rasterizing hundreds of 300 DPI pages in memory easily consumes dozens of gigabytes of RAM, triggering Linux Out-Of-Memory (`OOMKilled`) termination.
2. **Worker Restart Vulnerability:** Without checkpointing, a container restart at page 850 of 900 restarts the job from page 1, wasting time, compute, and third-party API spend.
3. **Excessive Latency:** Forcing a user to wait 15 minutes before they can ask a single question creates high bounce rates and poor perception of performance.
4. **Opaque UI:** A static spinner provides zero feedback on large files, leaving users wondering whether the system is progressing or deadlocked.

## Scope

### 1. Chunked, Resumable Job Checkpointing

Large documents are partitioned into discrete page batches (default batch size: 10–20 pages). Instead of executing as an atomic monolithic transaction, progress is checkpointed after every batch:

```
[Job Dequeued] ──► Inspect Checkpoint in DB
                     ├── Found: Resume from page N + 1
                     └── Not Found: Start from page 1
                     │
                     ▼
             Process Batch (Pages N to N + 20)
               ├── Render & Preprocess (Disk Spill)
               ├── OCR / Docling Parse
               ├── Chunk & Embed Batch
               └── Upsert Chunks into pgvector
                     │
                     ▼
             Durable Checkpoint Commit
               ├── Update jobs.payload.checkpoint
               ├── Update documents.pages_ready
               └── Publish SSE Progress Event
```

#### Checkpoint Contract (`packages/shared` & `konusbitr_worker`)
Store the durable checkpoint inside the `jobs` table `payload` column:
```jsonc
{
  "checkpoint": {
    "version": 1,
    "lastProcessedPage": 60,
    "totalPages": 900,
    "batchSize": 20,
    "updatedAt": "2026-09-12T15:45:00Z"
  }
}
```

- **Crash Recovery:** When a worker process crashes or restarts, its consumer reclaims the unacknowledged Redis stream message (`XREADGROUP`). The worker queries `jobs.payload.checkpoint`, reads `lastProcessedPage`, and resumes execution at page $61$.
- **Idempotent Upserts:** All database writes (chunks, pages, embeddings) use `ON CONFLICT (document_id, ordinal) DO UPDATE`, guaranteeing exact-once data integrity even under repeat delivery.

### 2. Memory Ceilings & Disk Spill Strategy

To prevent memory leaks and OOM crashes, workers operate under a strict **2GB RAM ceiling**:

- **On-Demand Rasterization:** Never load or retain the entire PDF in RAM. Render pages on-demand in batch increments using `pypdfium2`.
- **Ephemeral Disk Spill:** Rendered page bitmaps are written to a secured, temporary scratch directory:
  ```
  /tmp/konusbitr_scratch/{jobId}/page_{pageNo}.webp
  ```
- **Proactive Garbage Collection:** Once a batch is parsed and its elements converted into text, image buffers are flushed, scratch files unlinked, and Python's `gc.collect()` explicitly invoked.

### 3. Streamed Partial Readiness

Users should not wait for page 900 to complete before interacting with page 1:

#### Schema Additions (`packages/db/src/schema/documents.ts`)
```typescript
export const documents = pgTable('documents', {
  // Existing fields...
  pagesReady: integer('pages_ready').notNull().default(0),
  pagesTotal: integer('pages_total'),
});
```

#### Readiness Progression
1. **Initial Threshold:** Once the first batch (e.g. first 10 pages) is parsed, chunked, and embedded into pgvector, the worker updates the document status to `partially_ready`.
2. **Immediate Availability:** The web app viewer unlocks the document. The user can browse the initial pages and submit chat queries with clickable citations against the indexed subset.
3. **Non-Blocking Ingestion Banner:** The viewer displays an unobtrusive indicator:
   > "Indexing in progress: 140 of 900 pages processed. You can search and chat with ready sections."
4. **Final Transition:** When the final batch completes, document status transitions to `ready`, and the banner smoothly dismisses.

### 4. Document Ingestion Progress & Recovery UI

Replace the Phase 06 progress placeholder in `apps/web` with a complete, user-facing Ingestion Dashboard:

```
┌─────────────────────────────────────────────────────────────┐
│ Parsing Document: Annual_Report_2025.pdf                   │
│                                                             │
│ Stage: Optical Character Recognition (OCR)                  │
│ Progress: Page 142 of 900 [============>                 ]  │
│ Estimated Time Remaining: ~4 minutes                        │
│                                                             │
│ [ Cancel Ingestion ]                                        │
└─────────────────────────────────────────────────────────────┘
```

#### Key Capabilities
- **Granular Progress Reporting:** Real-time updates emitted over SSE (`stage`, `percent`, `pagesReady`, `pagesTotal`, `message`).
- **Dynamic ETA Calculation:** Rolling average processing time per page multiplied by remaining pages.
- **Job Cancellation:** A "Cancel Ingestion" button sends `POST /api/documents/:id/cancel`. This sets a cancellation key in Redis (`konusbitr:cancel:{jobId}`). The worker checks this flag between page batches, aborts execution, purges temporary scratch files, and marks the job `cancelled`.
- **Actionable Error States:** If terminal failure occurs (e.g., password-protected PDF, corrupt file, unsupported encryption), display human-readable guidance and an immediate "Retry with Settings" modal rather than raw stack traces.

### 5. Performance Budget

- **CPU OCR Benchmark:** A 50-page scanned document must reach `ready` status in **under 2 minutes** running on a 4-core CPU with standard concurrency (`WORKER_CONCURRENCY=2`).
- **Memory Ceiling:** A 900-page scanned document must execute without worker RSS memory exceeding 2GB at any point.

## Non-Goals for Phase 12.4/4

- Distributed multi-node cluster orchestration (e.g. Kubernetes Celery/Ray clusters) — single-node horizontal container concurrency is the architectural model.
- Document editing, page splitting, or page reordering (handled in Phase 13/14).

## Acceptance Criteria

- [x] **900-Page Scan Completion:** A 900-page scanned PDF successfully completes ingestion to `ready` status without triggering worker OOM errors.
- [x] **Resumable Checkpoints:** Simulating worker failure (`kill -9`) at page 450 causes the restarted worker to resume processing from page 451 without re-processing pages 1–450.
- [x] **Streamed Partial Readiness:** Chat answers with verified page citations become possible over the first 10 pages while the remainder of the document continues processing.
- [x] **Bounded Memory Usage:** Worker process memory (RSS) stays strictly under 2GB throughout the execution of the 900-page fixture.
- [x] **50-Page Performance Budget:** A 50-page scanned PDF completes OCR and reaches `ready` in under 2 minutes on a 4-core CPU.
- [x] **Interactive Ingestion UI:** The web UI displays real-time stage descriptions, page-level counters, rolling ETA, and an interactive "Cancel Ingestion" button that terminates the job within 2 seconds.
- [x] **Actionable Error Handling:** Intentionally corrupted or encrypted documents fail with descriptive, user-friendly error messages and a working Retry button.

## What was built, and where the specification was departed from

Two places, both recorded in `docs/adr/0008-resumable-ingestion.md`.

**The checkpoint's primary home is `parse_results.checkpoint`, not
`jobs.payload`.** It is still mirrored into `jobs.payload.checkpoint` for an
operator reading the job table, and nothing branches on that copy. The reason is
that the checkpoint and the partial artifact have to be written together or the
scheme is unsound — a checkpoint saying "page 850 done" beside an artifact
holding 800 pages resumes into a document with a hole in it — and the partial
artifact belongs in `parse_results` because that is where the finished one
lives. The rule that falls out of it is worth more than the storage choice: **a
row with a checkpoint is not a docId cache entry**, and both runtimes filter on
it.

**Cancellation stops at the next page rather than instantly.** The flag is
polled twice a second and consulted between pages, so a job stops within one
poll plus one page. Interrupting mid-page would leave half a reading written,
and finishing the page costs about a second. The *user-visible* two-second
budget is met by the web app marking the document `cancelled` and publishing the
final progress frame when the button is pressed; the worker's durable write
follows a page later, and the two are idempotent.

Everything else is as specified. The disk spill is
`/tmp/konusbitr_scratch/{jobId}/page_{n}.webp`, swept at worker startup as well
as on job exit; `documents.pages_ready` / `pages_total` carry partial readiness;
`partially_ready` unlocks the viewer and chat; `POST /api/documents/:id/cancel`
and `POST /api/documents/:id/retry` are the two new routes, both org-scoped
through `withAuth` and both `documents:write`.
